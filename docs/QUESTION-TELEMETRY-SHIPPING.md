# Question telemetry shipping — prepared, not activated

The runtime adapter emits a pure JSON line per completed/failed/aborted observed
question attempt. This host job reads only the uniquely labelled production
`apicompass-prod` / `chat` container's Docker logs. It does not inspect prompts,
request bodies, provider keys or process environments. It does not read SSM.
No AWS calls, production jobs, unit installation or timer activation were
performed while implementing this shipper.

## Frozen runtime event contract

| Field | Accepted value |
| --- | --- |
| event | `question_attempt` |
| schema_version | integer `1` |
| request_id | canonical UUID generated by adapter, opaque to shipper |
| app_version | 1–64 ASCII letters/digits/dot/underscore/hyphen, matching the frozen hook grammar |
| librechat_version | `0.8.8` |
| outcome | `succeeded`, `failed` or `aborted`, consistent with reason |
| reason | one of the exact enums below |
| duration_ms | finite number from 0 through 300000; booleans rejected |
| timestamp | real ISO8601 UTC date/time ending `Z`, at most six fractional digits |
| http_status | integer 0 through 599; booleans rejected |

Reason `success` means succeeded. `disconnected` and `aborted` mean aborted.
All other accepted reasons mean failed: `provider_error`, `uninspectable_stream`,
`unfinished`, `missing_final`, `capacity_exceeded`, `observation_timeout`,
`http_error`, `invalid_start_response`, `duplicate_start`, `shutdown`.

The adapter uses `process.stdout.write(JSON.stringify(event)+'\n')`; no logger
prefix is accepted. Docker's optional RFC3339 timestamp prefix is removed.
Unrelated diagnostics/non-JSON are ignored. A recognized event with missing or
invalid fields fails the scan without advancing state or emitting a healthy
heartbeat. Unknown event fields are stripped, including prompt/error/header
fields, even if future runtime code accidentally adds them. Only the ten fields
above can reach CloudWatch. CLI failures expose a fixed failed status, UUID
request ID and elapsed time, never child output or exception text.

An AnswerSuccess means the adapter observed a successful terminal answer;
it does not independently score factual correctness or completeness. A provider
error within an HTTP 200 stream must be failed by the adapter. Questions that
never produce adapter events cannot be inferred by this shipper. Controlled
adapter success/provider-error/aborted tests remain necessary on the host.

## Delivery, heartbeats and bounded state

Use Linux Python at `/opt/apicompass-tools/bin/python`, boto3 from the host
bootstrap, Docker and the existing instance profile. `AWS_REGION` defaults to
`ap-southeast-1`. The unit reads existing **nonsecret** `/etc/apicompass/ops.env`.
It does not require a new secret, database, static credential or IAM grant.
Existing permissions are CreateLogStream/PutLogEvents for the already-created
14-day `/apicompass/prod/questions` group and PutMetricData namespace APICompass.
The script never creates a log group or changes retention.

Each new UUID is shipped as bounded clean JSON to a daily
`question-attempts-YYYY-MM-DD` log stream. Only after Logs accepts the batch and
CloudWatch accepts both counters does the script atomically replace its state:

- Namespace `APICompass`, dimension **only** `Project=APICompass`, unit Count.
- `AnswerSuccess`: number of new unique succeeded attempts in that scan.
- `AnswerFailure`: number of new unique failed **or aborted** attempts.
- An available, successfully scanned chat with no new attempts publishes **zero
  for both metrics**. Idle chat therefore has a heartbeat without fake questions.
- Unavailable/ambiguous chat, failed log scan, invalid event, state error or AWS
  delivery failure fails the service. It does not manufacture a zero heartbeat.
  Configure missing metric periods as breaching; a dead host cannot emit a failure.

State is `/var/lib/apicompass-telemetry/state.json`, mode 0600 inside a mode-0700
directory. It contains only UTC cursor and UUID/timestamp dedup metadata.
`ship.lock` prevents overlapping host invocations. No raw Docker lines are
written to disk or state. A five-second cursor overlap catches scan-boundary
events; UUID dedup handles overlap/repeated lines. Seen IDs are retained for 24
hours, maximum 10000. Initial deployment scans the preceding ten minutes only.

Per scan limits: 20 seconds Docker stream reading, 4 MiB total raw bytes,
4096 bytes per line, 500 candidate events, 1 MiB state. Exceeding bounds fails
without cursor advance; no silent truncation pretends complete delivery.
An oversized unrelated log line also fails the bounded scan. Investigate log
volume/format and preserve diagnostic timestamps through a private operator
session; do not export arbitrary raw logs into evidence. The timer may skip a
minute while the same oneshot is still active; the next invocation resumes from
its last committed cursor.

Cross-service **exactly-once delivery is not promised**. Logs can be accepted
before metric/state failure; a retry can duplicate logs and increment counts
again. A lost metric success response or failure to save state has the same
at-least-once ambiguity. UUIDs allow later log deduplication. State advances only
after both APIs report success; partial log rejection also prevents advancement.
Consequently alarm on failure **greater than zero**, and do not present these
counts as a guaranteed exact assistant accuracy denominator. Deleting state
can replay ten minutes and duplicate counts; do not casually reset it.

Docker rotation/deletion, replacing a chat container before its logs are shipped,
clock errors and downtime beyond retained Docker history can cause unrecoverable
gaps. This script cannot retrieve an old removed container. Monitor shipping and
capture a clean pre-replacement run; do not claim unlimited durable ingestion.

## Future host installation and acceptance

Execute only on the approved host after the new adapter emits its contract,
with no secrets in shell tracing or output. In a root session:

```sh
cd /opt/apicompass
cp infra/systemd/apicompass-question-telemetry.service /etc/systemd/system/
cp infra/systemd/apicompass-question-telemetry.timer /etc/systemd/system/
systemd-analyze verify /etc/systemd/system/apicompass-question-telemetry.service \
  /etc/systemd/system/apicompass-question-telemetry.timer
systemd-analyze calendar '*-*-* *:*:00 UTC'
systemctl daemon-reload
systemctl start apicompass-question-telemetry.service
systemctl show apicompass-question-telemetry.service -p Result -p ExecMainStatus
journalctl -u apicompass-question-telemetry.service -n 12 -o cat --no-pager
# After private readback confirms clean events and both metric heartbeats:
systemctl enable --now apicompass-question-telemetry.timer
systemctl list-timers apicompass-question-telemetry.timer --all
```

Require two real scheduled successful runs, one genuine successful app answer,
one controlled provider failure/aborted attempt, CloudWatch event field audit,
correct success/failure metrics, idle zeros, real alarm/email delivery and
recovery. Confirm duplicate source UUIDs do not add counts after committed state.
AWS API readback requires operator access; the runtime role deliberately lacks
GetMetricData/GetLogEvents. Do not broaden its permissions for readback.
Do not use a fake metric or synthetic injected production log as evidence of a
real provider failure. Record remaining gaps explicitly.

Offline tests exercise parser/privacy, malformed metadata, dedup, zero-heartbeat,
bounded batches, successful state commit, partial delivery/retry and sanitized
failure output. Windows tests do not exercise Linux selectors/flock/systemd or
real Docker/AWS delivery. Those remain host acceptance gates.
